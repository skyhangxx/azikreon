Дата: 15 сентября 2026. Проверены локальные исходники и сборка; отдельные production-проверки выполнены только чтением. Рабочие данные CMS/CRM, пользователи, домен и настройки хостинга не изменялись. Дизайн, CSS, тексты страниц и сценарий отправки заявок сохранены.

### Что сознательно не переделывалось

- Исходные миграции `001` и `002`, основные RLS-политики CMS, Supabase project, publishable key, CRM endpoint и формат ответа сохранены.
- Публичный bucket сохраняет прямые URL всех изображений, включая изображения скрытых записей, если URL известен. Скрытие записи защищает её текст через RLS, но **не делает её файл конфиденциальным**. Перевод bucket в private потребует другого способа выдачи URL и отдельной проверки существующих изображений; автоматического переключения не было. Это свойство [публичных bucket в Supabase](https://supabase.com/docs/guides/storage/buckets/fundamentals).
- Правила Storage относятся ко всему CMS: администраторы сайта могут управлять общими изображениями. Это не система отдельных личных хранилищ каждого администратора. Ограничение удаления не предназначено для защиты от уже доверенного администратора, сознательно изменяющего записи CMS/реестр.
- Публичный Apps Script endpoint остаётся доступен напрямую. Проверка honeypot, лимит по телефону и дедупликация не останавливают бота, меняющего телефон и request_id. Полной защиты от распределённого спама и расходования квот нет; CAPTCHA и новые сервисы не добавлялись.
- `check-mobile.mjs` не прошёл: в последовательном сценарии `/test/` при 320 px он получил 329 px. Отдельная проверка той же страницы после загрузки показала 320 px без переполнения. Ожидание загрузки и шрифтов не устранило расхождение в старом check; причина не установлена. Изменения CSS не вносились, утверждения об исправлении этого случая нет.

## 2. Проверенные механизмы защиты

### Секреты и зависимости

- Поиск охватил локальные текстовые исходники, конфигурацию, `dist`, текст/XML внутри ZIP и DOCX, доступные текстовые Git-объекты. На первичном проходе: 118 файлов, 94 текстовых элемента архивов, 37 Git-объектов. Проверялись `.env`, приватные ключи, секретные Supabase-ключи, JWT, GitHub/Google-токены, строки подключения с паролем и присваивания credentials/password.
- Найденные совпадения относились к `credentials: 'omit'`, внутреннему коду SDK и явно тестовому refresh token в `tools/cms-fixture.js`. Действующих секретов не выявлено. OCR изображений, извлечение текста из PDF и проверка удалённой истории/недоступных Git-объектов не выполнялись.
- Во frontend стоит публичный publishable key. Проверка конфигурации отвергает secret key и JWT с ролью, отличной от anon. Spreadsheet ID и публичный `/exec` endpoint сами по себе не являются паролями.
- Runtime CDN нет: Supabase JS 2.57.4 хранится локально, лицензия остаётся в сборке. Включён Auth JS 2.71.1; опубликованная [GHSA-8r88-6cj9-9fh5](https://github.com/supabase/auth-js/security/advisories/GHSA-8r88-6cj9-9fh5) касается более ранних версий. Оснований обновлять SDK только из-за его возраста не установлено; это не полная гарантия безопасности всех транзитивных компонентов.
- В коде приложения нет eval/new Function и обработчиков произвольных cross-origin postMessage. В vendor найден стандартный fallback `new Function('return this')` для получения глобального объекта и сообщения BroadcastChannel/Worker; пользовательская строка как код им не передаётся. Библиотека не переписывалась.

### Auth / RLS / Storage

- `cms_private.admins` закрыта от PUBLIC, anon и authenticated. Проверка роли использует `auth.uid()`, а не ID, присланный frontend.
- `cms_is_admin()` и `cms_unused_media()` — security definer с пустым search_path и квалифицированными именами. Execute ограничен существующими GRANT/REVOKE. Обычная регистрация в Auth сама по себе не создаёт администратора.
- RLS включён на `cms_teachers`, `cms_reviews`, `cms_media` и `cms_private.admins`. Контент доступен публично только при `is_published`; CRUD требует admin-role. Прямые SQL-запросы от anon/non-admin отвергнуты в тестовой БД. Отзыв admin-записи немедленно блокирует изменения даже существующим пользователем.
- Bucket допускает JPG/PNG/WebP и ограничивает размер 5 МБ на стороне Storage. UI дополнительно проверяет сигнатуру файла и 24 мегапикселя. Проверка сигнатуры/декодирования в UI не является серверной проверкой байтов; MIME нельзя считать антивирусной проверкой. Загрузка доступна только администратору.
- Имена генерируются через `crypto.randomUUID()`, SQL и клиент ограничивают путь и расширение. Перезапись существующего объекта не разрешена; новое фото получает новый путь. Удаление использованных фото, включая фото скрытых записей, блокируется.
- Панель и редактор закрыты до проверки роли. Пароль не сохраняется в localStorage, очищается после каждой попытки входа; токены админки хранятся в sessionStorage. Проверены истёкший refresh token и неуспешный logout.
- Logout очищает сессию этого браузера. Уже выданный JWT не становится автоматически недействительным в момент выхода: сервер проверяет срок JWT и актуальную admin-role. Это не обещание мгновенной глобальной отмены украденного access token.

### XSS, формы и навигация

- Имена, местоположения, описания и отзывы из CMS выводятся через textContent/DOM API. URL изображения формируется только для разрешённого локального пути или CMS bucket. Проверены javascript:, внешние URL, traversal и SVG-пути.
- Оставшиеся innerHTML — локальные шаблоны навигации/SVG и ответы из статического `test-config.js`; контент Supabase, query/hash или текст посетителя в них не подставляется. Эксплуатируемого XSS-вектора в этих местах не установлено.
- Переход после теста имеет фиксированный локальный адрес. Пользовательский query/hash не управляет URL перехода. В аналитические события формы не передаются имя, телефон и email; логирования паролей/заявок в приложении не обнаружено.
- CRM сохраняет текущие endpoint, `text/plain` транспорт и подтверждение `{ok: true, request_id}`. HTTP 200 без совпадающего ID не считается успехом.
- Повтор после сетевой ошибки сохраняет ID и данные; успешная отправка блокирует повторный клик. Согласия проверяются на сервере. Группа и result_id вычисляются сервером по баллу; сам балл статического теста нельзя считать подтверждённым экзаменационным результатом.
- Honeypot теперь остаётся в payload для серверной проверки. UTM ограничены пятью используемыми ключами и длиной 500; произвольные `utm_*` больше не попадают в отправку.
- Apps Script отклоняет неизвестные поля, неверные типы, слишком длинные значения, некорректный JSON и тело свыше 16000 символов. Дедупликация остаётся под ScriptLock; сохраняется лимит 5 новых заявок на телефон. Формулы с `=`, `+`, `-`, `@` и ведущими пробельными символами экранируются перед appendRow. Тесты не записывают данные в Google.

### GitHub Pages / индексация

- Текущая сборка содержит 231 публичный файл: страницы, ресурсы, юридические PDF/DOCX и пять файлов public. Сохранены `/admin`, пользовательский `/test`, `/test/result`, `/application`, `/thanks` и юридические страницы.
- В dist нет SQL, tools, `.env`, CRM-архива, Apps Script, внутреннего отчёта и README. MIT-лицензия SDK сохранена. Неожиданный файл в public/assets вызывает ошибку сборки; новый допустимый вид ресурса нужно явно добавить в allowlist.
- Sitemap содержит только главную и `/test/`; административных страниц нет. Canonical-тегов в исходниках нет, ошибочных canonical не найдено. Favicon главной подключён в основном `index.html` как `/favicon.png`.
- Robots.txt — инструкция поисковику, не контроль доступа. Статические исходники `/admin` могут быть прочитаны любым посетителем; права на данные обеспечиваются Supabase.
- URL изменённых JS и импорта общего CMS-клиента получили версию `20260915-security`, чтобы новый admin.js не загрузил старый закэшированный cms-client.js. Это важно на GitHub Pages, где локальный `_headers` не управляет кешированием.
- На GitHub Pages нельзя настроить собственные HTTP CSP/frame-ancestors, X-Frame-Options, X-Content-Type-Options, Permissions-Policy, HSTS, Cache-Control и X-Robots-Tag через `_headers`. Часть CSP и referrer policy допускает meta, но frame-ancestors/X-Frame-Options так не работают. Строгая CSP без проверки реального окружения не добавлялась. [Документация CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy), [пример хоста с поддержкой _headers](https://developers.cloudflare.com/pages/configuration/headers/).

## 3. Что подтверждено на production только чтением

- `https://akizkorean.ru/admin/`: HEAD 200, `server: GitHub.com`. CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, HSTS и X-Robots-Tag в ответе отсутствовали. Это замер одного ответа, а не всех страниц/CDN-узлов.
- GET `cms_is_admin` с публичным ключом: false.
- GET скрытых преподавателей и отзывов с выборкой только ID: 0 строк. Это согласуется с RLS, но само по себе не доказывает существование скрытых записей.
- GET реестра медиа: 401; обращение к `cms_private`: 406, строк не возвращено.
- GitHub API без авторизации вернул 404 для настроенного origin. Это не подтверждает публичность и не позволяет отличить private от отсутствующего/недоступного репозитория. Локальный Git отслеживает исходники, а dist игнорируется: этот исходный репозиторий нельзя делать публичным по условиям проекта.
- Авторизованный production CRUD, действующий набор всех RLS-политик/GRANT, Storage MIME-ограничения в Dashboard, Auth signup/session settings и опубликованная версия Apps Script **не проверены**. Нельзя считать локальные тесты доказательством совпадения production с SQL/Code.gs.

- Проверены синтаксис всех JS/MJS приложения и tools, все 16 результатов теста, CRM retries/consent/error/success, XSS-строка в CMS, admin CRUD, ошибки сети, смена роли, logout во время upload и ошибка серверного logout.

Повторный импорт CMS с другим query создавал отдельный модуль с автозагрузкой: тест теперь переиспользует уже загруженный экземпляр.
- Для браузерных checks нужен изолированный Chrome с CDP на `127.0.0.1:9223` и локальный сервер на `127.0.0.1:4173`. Runner рассчитан только на этот тестовый браузер: он закрывает старые тестовые вкладки. Подставные CMS-данные живут только в браузере; внешние CMS/CRM-запросы заблокированы. PGlite можно установить в `.cache/cms-db` с `--ignore-scripts`; production-зависимости не добавлены.

## 6. Необходимые действия владельца

### Supabase Dashboard

1. Выполнить **только новую** `supabase/003_storage_cleanup_guard.sql` в SQL Editor действующего проекта после уже существующих 001/002. Она меняет политику, не создаёт пользователей и не изменяет контент.
2. При проверке production сопоставить фактические RLS/GRANT с файлами: наличие посторонней разрешающей policy может расширять доступ. В `cms_private.admins` должны быть только назначенные администраторы, схема не должна быть exposed API schema. Bucket `cms-images`: 5 МБ, MIME JPEG/PNG/WebP, запись только по admin-role. Эти настройки не были доступны для подтверждения через публичный ключ.

### Google Apps Script

1. Сохранить текущую версию для отката, обновить код из `integrations/google-sheets/Code.gs`.
2. Опубликовать новую версию **того же развертывания** через управление развертываниями. URL `/exec`, spreadsheet ID, колонки и frontend config не менять. `setupCrm` заново не нужен для настроенной таблицы.
3. Пока этого не сделано, новые server-side проверки не работают в production.

### GitHub

- Опубликовать содержимое обновлённого dist существующим способом. В публичный репозиторий не отправлять корень проекта, SQL, инструменты, этот отчёт и CRM-архив.
- Подтвердить видимость исходного репозитория в настройках: неавторизованный API не позволил её установить. Если он уже private, менять ничего не нужно. Реальная публикация в этом аудите не выполнялась.

### REG.RU

Изменения не требуются: домен и DNS не менялись, HTTPS-сайт отвечает. Добавление proxy/нового хостинга ради заголовков в эту работу не входит.

## 7. Проверки после деплоя

1. Открыть главную, `/test`, `/application`, `/thanks`, `/admin` и юридические документы; проверить favicon, CNAME, robots/sitemap и verification-файл. Проверить отсутствие SQL/tools/архива в опубликованном дереве.
2. Войти существующим администратором и проверить работу CMS; обычная существующая Auth-учётная запись без admin-записи не должна иметь CRUD/upload. Не создавать фиктивный публичный контент ради проверки; локальные негативные CRUD-тесты уже выполнены.
